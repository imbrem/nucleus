# Nucleus — Agent instructions

Read `README.md` for project overview, architecture, and crate map.

## Build and test

```sh
glu test --cargo     # fast: Cargo tests only
glu test             # full: Buck + Cargo + Wasm + pnpm
glu lint             # clippy (deny all + pedantic) + prettier
glu fmt              # rustfmt + prettier
glu check            # cargo check + buck2 build
glu buck sync        # regenerate BUCK files after dependency changes
glu buck check       # verify BUCK files match Cargo metadata
```

After adding or removing crates or changing dependencies, always run
`glu buck sync` and commit the generated BUCK and JSON files.

## Code conventions

- Edition 2024, Rust 1.97, resolver 3.
- `#![deny(unsafe_code)]` on all crates except `crates/lib/sqlite/src/vfs/ffi.rs`.
- `clippy::all` and `clippy::pedantic` are denied workspace-wide.
- All crates: version `0.0.0`, license `CC0-1.0`, `publish = false`.
- External dependencies are wrapped in `crates/lib/*` facade crates; product
  code never depends directly on third-party crates.
- Dual build system: Cargo is authoritative; BUCK files are generated by
  `glu buck sync`. Every new crate needs both `Cargo.toml` and a BUCK file.

## Architecture

### Layering

```
bin/nucleus  →  nucleus  →  neutron  →  lib/sqlite
                                    →  lib/error
                            proton  →  lib/wasm
                            data/*
                            lib/hash, lib/rand, lib/crypto
```

Dependencies point downward. Never introduce upward or circular dependencies.

### Trust boundary

- **Neutron** is deliberately permeable: callers can access raw SQLite.
- **Nucleus** is opaque: it wraps Neutron and never exposes the inner
  connection. All trusted state changes go through Nucleus.
- Rows do not mint facts. Only checked nucleus transitions construct
  theorem authority.
- No database row, URL, or imported data grants trust or effect
  capabilities. Trust enters through connection-opening policy and
  explicit checked transitions.

### Key abstractions

- `Obj<N: Namespace>` — fixed-width namespaced identifier (`O256 = Obj<Cov>`)
- `Connection` (neutron) — permeable SQLite wrapper with connection metadata
- `Connection` (nucleus) — opaque policy wrapper over neutron
- `Cas<'conn>` — connection-local content-addressed store (BLAKE3)
- Bootstrap catalog — `(table_name TEXT PK, interpretation TEXT NOT NULL)`

### Connection metadata

Lives in SQLite `TEMP` tables prefixed `cov_conn_`. Not serialized with
database images. Includes:
- `cov_conn_catalog` — connection-local table registry
- `cov_conn_attached` — attached database registry
- `cov_conn_default_cas` — default content-addressed store

### Design approach

Follow the concrete-first approach: implement specific capabilities before
extracting generic traits. Extract traits only after at least two concrete
consumers establish the required interface shape.

Separate relational denotation (which tuples) from computational
realization (how to obtain them). Resolvers are untrusted; their output
is always validated before entering trusted state.

## Key files

- `crates/lib/hash/src/lib.rs` — `Obj<N>`, `Namespace` traits, macros
- `crates/lib/hash/src/blake3/` — BLAKE3/Cov namespaces, tree operations
- `crates/lib/sqlite/src/vfs/` — VFS trait API, FFI, registry
- `crates/neutron/src/connection.rs` — Neutron connection + metadata
- `crates/neutron/src/cas.rs` — Content-addressed store
- `crates/neutron/src/image.rs` — Database image serialize/deserialize
- `crates/nucleus/src/connection.rs` — Nucleus policy wrapper
- `tools/glu/` — Build tool (separate workspace)
